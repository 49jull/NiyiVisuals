# Niyi Visuals project rules

## Project and sources

- The application root is `niyi-visuals-product-handoff/`; run future package/build commands there. The surrounding workspace is the Git repository root. Keep the supplied package intact.
- Read `niyi-visuals-product-handoff/PRODUCT.md` first. It is the primary specification. Then read its `outputs/redesign-strategy.md`, `outputs/content-inventory.md`, and `outputs/asset-register.md`, plus the JSON asset/link registers and relevant evidence. These are the supplied research documents; there is currently no `research/` directory.
- Follow current user instructions over older planning sequences. See `IMPLEMENTATION_PLAN.md` for stages, decisions and dependencies. Do not repeat the completed discovery crawl or reopen the selected concept.
- Preserve supplied research and evidence. If a future approved specification change is necessary, update canonical `PRODUCT.md` and its identical `outputs/PRODUCT.md` distribution copy together, and refresh affected handoff manifest entries.

## Scope and review gates

- Current scope is the complete local editorial portfolio: Home/Work, Grid/Index/filtering, static project URLs, About and Contact entry points, preview and validation. No external Site registration, public deployment, client-site edits or real inquiry submissions are authorized.
- The user explicitly superseded the homepage-only gate on 16 November 2026. Implement the requested core experience; services continue to their original authoritative page until their commercial terms are clarified.
- Owner editing/CMS choice is deferred until after homepage review. The implemented stack is Astro with strict TypeScript, static HTML, plain CSS and a React/Motion gallery island. Hosting selection and live Pixieset migration remain unapproved.
- Changes to client hosting/domain, publication, real message tests and new paid services need their own applicable user authorization.

## Content and design

- Implement PRODUCT.md v2.1’s user-authorized editorial redesign: near-white, charcoal, restrained vermilion and one Plus Jakarta Sans family. Use stable photographic identities, connected Grid/Index/filtering and shared photograph-to-project transitions. Preserve the client truth behind “On Both Sides”; the earlier dark layout and mono roles are historical.
- Use the client's registered photographs. No stock/generated portfolio images, invented logo, business claims, captions, endorsements, pricing interpretations or placeholder marketing copy.
- Preserve all eight source routes and account for all 100 image placements. Keep category mappings authoritative and correct; `/gallery-4/` is an honest 404 pending historical clarification, not a fourth gallery.
- Preserve exact source copy separately from approved display copy. Inventory summaries are not verbatim copy. Keep provenance and approval records in development-only data; explicitly project approved public fields into rendered content.
- Preserve literal service strings until owner clarification. Do not infer currency, normalize ambiguous terms, add a WhatsApp number or promise response times.

## Implementation and verification

- Prefer reusable semantic components, typed content/asset records, CSS custom properties and small progressive browser enhancements. Keep important content/navigation usable without JavaScript. Add dependencies only for demonstrated needs.
- Keep research, evidence, masters, internal ledgers and credentials outside public output. Optimize web image derivatives separately; verify dimensions, focal points, alt text and provenance. Never guess Pixieset variant URLs or deduplicate by filename alone.
- Apply available relevant skills: Impeccable context once per design session and craft-floor immediately before UI edits; fresh web-design-guidelines at UI review; React rules only if React is introduced; Sites workflow only within authorized local/hosting scope. Sites Remix requires an actual Sites source and remix request.
- Target WCAG 2.2 AA, visible focus, correct modal focus/Escape/return, readable responsive layouts, reduced motion and stable image geometry. Follow PRODUCT.md's test matrix and performance budgets.
- Run appropriate type/build checks and meaningful route, asset, focus and inquiry-state checks as features land. Review rendered desktop/mobile together, batch material fixes, and respect the homepage gate. Report what was tested separately from unverified or owner-dependent behavior.
- Inquiry success requires actual provider acceptance; receipt needs an arranged test. Never simulate success or reuse Pixieset tokens. Keep secrets on the server and user input intact after failure.
